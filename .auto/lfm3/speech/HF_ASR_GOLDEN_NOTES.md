## The 12.5 tokens/audio-s cross-check (the reason this golden exists)

HF's own feature extractor defines the token law in its own file:

```python
def pad_length(self, num_samples):        # identical to lfm3_mel.c's padding rule
    if num_samples < self.n_fft: return self.n_fft
    return num_samples + (-(num_samples - self.n_fft) % self.hop_length)
def num_frames(self, num_samples):        return 1 + (self.pad_length(num_samples) - self.n_fft) // self.hop_length
def num_encoder_tokens(self, num_frames): return -(num_frames // -self.encoder_stride)
```

For the fixture (2,075,520 samples @ 16 kHz): `num_frames = 12971`,
`num_encoder_tokens = ceil(12971/8) = 1622`. HF fed **1622** audio embeddings to the
backbone; our engine's law (run #303: 12.5 tokens per audio second, 100 mel frames/s,
stride 8) predicts **1622**. `hf_asr_golden.json:crosscheck_vs_engine.match = true`.
Prompt layout: 1642 tokens = 1622 audio placeholders + 20 text tokens.

## HF's own ASR quality on this fixture (not our engine's)

WER against the authored transcript: **36.07%** over 280 reference words
(substitutions 12, deletions 89, insertions 0) with `max_new_tokens=1024` and EOS
emitted — i.e. HF stopped after 191 words. Read this as *the reference's ASR quality on
a TTS voice*, and read our engine's acceptance against **HF's output** (`output
.decoded_text_sha256`, token ids in the JSON), never against the authored transcript:
penalising our engine for HF's deletions would be measuring HF.

## Environment warnings seen, and what they do and do not affect

* `The tokenizer you are loading ... with an incorrect regex pattern ... set
  fix_mistral_regex=True`. This is the tokenizer's decode/normalization path. It affects
  how the generated ids are rendered to text, not the ids, so the golden's token ids are
  the durable artifact and the text is a convenience view. It is also the same
  tokenizer-config family of defect the S1 gate was built around
  (`tokenizer_config.json` ships `pre_tokenizer: null`; the engine uses the GPT-4 `Split`
  regex + ByteLevel + `ignore_merges=True`), and it is why S1's bar is 531/531 fixtures
  id-for-id rather than a text comparison.
* `causal_conv1d_fn is falling back to its reference PyTorch implementation` — correct
  results, much slower. Host decode rate measured 3.26 s/token for the first (cold)
  generation and 0.62 s/token warm, on top of the host GPU. Nothing in the golden
  depends on speed.

## The embedding matrix, and the open comparison

`hf_audio_embeddings_1622x2048.f32` = HF's `get_audio_features` output, fp32, row-major
`[1622, 2048]`, sha256 recorded in the JSON's `embedding_matrix` block with per-row L2
stats. Against our encoder's `proj_out`:

| | HF | engine | C reference (30 s) |
|---|---|---|---|
| mean row L2 | 1.6028 | 1.2791 | — |
| per-row cosine, rows 0-2 | — | 0.99997 | 0.99997 |
| per-row cosine, rows 3-20 | — | 0.9998 | 0.9998 |
| per-row cosine, rows 100+ | — | 0.85 (mean) | 0.912 |
| per-row cosine, rows 300+ | — | — | 0.877 |

Two facts localize it, both measured:

1. **The C reference shows the same position-growing decay.** It is x86, independent of
   the CUDA code, and matches the numpy spec re-derivation of §22 to 3.3e-6 — so this is
   not a GPU bug.
2. **It is not an alignment offset.** Scanning shifts k = -6..+18 puts the optimum at
   k = 0 (cos 0.923) with a sharp falloff (0.672 at k=-1, 0.592 at k=+1): rows line up.

Leading hypothesis: HF runs the audio tower in bf16, whose rounding grows with position
(longer attention prefixes, deeper residual stream), which is exactly consistent with
the 4 s fixture (rows < 50) matching HF to 2.2e-6 in §22. The test that settles it is
the fp32 numpy reference at `Tm=2999` vs HF: if an independent fp32 implementation shows
the same 0.92, then HF's bf16 tower is the outlier and the encoder's acceptance gate is
end-to-end (speech in -> greedy text vs this golden), not embedding-level.

## What this golden does NOT certify

The fixture is a **gTTS-synthesized voice** (see `manifest.json`): it measures timing and
greedy token-stream agreement on speech-shaped audio, and certifies nothing about
speaker, accent, noise, channel, or disfluency robustness. HF's transcription is the
arbiter for the audio path; the authored transcript is provenance for the fixture, not a
target.
